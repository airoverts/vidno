# AGENTS.md — Vidno

## Проект

Vidno — веб-сервис для мониторинга и развития видимости бренда в AI-ответах. Основной пользователь — in-house маркетолог.

- `index.html` — лендинг и маркетинговые разделы.
- `dashboard.html` — отдельный рабочий интерфейс с левой панелью, live-проверкой и Планом роста.
- Личный кабинет клиента развивать внутри `dashboard.html`, не создавать для него отдельное приложение без прямого запроса.
- `css/style.css` — общий стилевой файл и дизайн-токены.
- `js/script.js` — логика лендинга.
- `js/auth.js` — клиентская проверка cookie-сессии и выход из аккаунта.
- `js/dashboard.js` — навигация dashboard, работа с API, live-проверка и План роста; `localStorage` используется только для локальных настроек интерфейса, например выбранного активного бренда.
- `backend/main.py` — FastAPI API.
- `backend/database.py`, `backend/auth.py`, `backend/storage.py` — PostgreSQL, авторизация и хранение рабочих данных.
- `backend/cache.py` — PostgreSQL-кэш запросов и результатов.
- `backend/gigachat_client.py`, `backend/deepseek_client.py`, `backend/yandex_client.py`, `backend/openai_client.py`, `backend/gemini_client.py`, `backend/perplexity_client.py` — провайдеры моделей и анализа.
- `backend/search_collector.py`, `backend/rag_analysis.py` — сбор источников и структурный анализ.
- `docker-compose.yml` — PostgreSQL, FastAPI backend, Nginx frontend и сервис резервного копирования PostgreSQL.

## Backend и данные

- PostgreSQL используется для пользователей, сессий, брендов, проверок и задач Плана роста. Основные рабочие данные dashboard не считать данными только из `localStorage`.
- Авторизация работает через HttpOnly cookie-сессии. Не возвращать и не хранить токен сессии в `localStorage`.
- `GET /api/health` возвращает состояние backend и провайдеров.
- `POST /api/check` и `POST /api/check-all` выполняют проверки AI-видимости; проверки сохраняются в PostgreSQL.
- Бренды, история проверок, задачи Плана роста и скрытые возможности доступны через пользовательские API и изолированы по пользователю.
- `DELETE /api/cache` очищает общий кэш и для удалённого вызова защищён административным токеном.
- Для локальной разработки frontend использует `http://localhost:8000/api`; при едином origin — `/api`.
- Профиль пользователя и изменение пароля доступны в кабинете; админ-панель доступна пользователям с ролью `admin` и управляет статусами, тарифами и квотами клиентов. Полноценное восстановление пароля по email пока не реализовано.

## Версионирование и релизы

- Стабильные версии Vidno нумеровать по Semantic Versioning в формате `vMAJOR.MINOR.PATCH`. Первый стабильный релиз — `v1.0.0`, тег указывает на production-коммит `f830481`.
- `PATCH` повышать для обратно совместимых исправлений ошибок и уязвимостей, небольших интерфейсных изменений и внутренних улучшений без изменения пользовательских или API-контрактов: `v1.0.0` → `v1.0.1`.
- `MINOR` повышать при добавлении обратно совместимой функциональности, новых экранов, возможностей или API-методов: `v1.0.1` → `v1.1.0`.
- `MAJOR` повышать при несовместимых изменениях HTTP API, форматов данных, обязательных миграциях с нарушением обратной совместимости или крупной переработке продукта: `v1.1.0` → `v2.0.0`.
- Для предварительных сборок использовать суффикс `-rc.N`, например `v1.2.0-rc.1`. Такие версии не считать стабильными и не обозначать как latest release.
- Версию выбирать по наиболее значимому изменению относительно последнего стабильного тега. При повышении `MINOR` сбрасывать `PATCH` в `0`, при повышении `MAJOR` сбрасывать `MINOR` и `PATCH` в `0`.
- Каждый стабильный тег должен указывать на точный коммит, проверенный на тестовом сервере и предназначенный для production. Создавать аннотированный тег и одноимённый GitHub Release с заголовком `Vidno X.Y.Z` и краткими заметками на русском языке.
- Опубликованные теги и релизы не перемещать, не переиспользовать и не изменять задним числом. Исправление выпущенной версии оформлять новой `PATCH`-версией.
- Последовательность релиза: тесты → тестовый сервер → проверка → тег и GitHub Release → деплой того же коммита на production → проверка production.
- Не повышать версию, не создавать тег и не публиковать GitHub Release без прямого разрешения пользователя.

## Серверы и эксплуатация

### Домашний сервер

Это старый домашний экземпляр Vidno. Его не изменять во время работ на Timeweb.

- SSH: `ssh -o BatchMode=yes -o StrictHostKeyChecking=yes boss@192.168.0.101`
- Каталог проекта: `/home/boss/projects/vidno/vidno`
- Запуск: Docker Compose
- Frontend: Nginx на порту 80
- `/api/`: проксируется во внутренний FastAPI backend
- Базовая проверка:

  ```bash
  cd /home/boss/projects/vidno/vidno
  docker compose ps
  curl -i http://127.0.0.1/api/health
  ```

### Timeweb-сервер (production)

Это основной публичный production-сервер Vidno.

- SSH с текущего ПК: `ssh -o BatchMode=yes -o StrictHostKeyChecking=yes egor@72.56.15.118`
- Подключаться как `egor`; прямой SSH-вход как `root` не использовать. Для команд в `/root/projects/vidno/vidno` и Docker использовать `sudo -n`; доступ без пароля проверен. Скрипт команд можно передавать через SSH в `sudo -n bash -s`.
- Каталог проекта: `/root/projects/vidno/vidno`
- Git-ветка: `main`
- Домен: `vidno.one`
- Frontend: Nginx в Docker Compose, порты 80 и 443
- `/api/`: проксируется во внутренний FastAPI backend
- TLS-файлы находятся вне репозитория:
  - `/etc/vidno/tls/fullchain.pem`
  - `/etc/vidno/tls/privkey.pem`
- Права на TLS-файлы: `600`; содержимое сертификата и ключа не копировать в чат, Git или логи.
- Production `.env` находится на сервере и не входит в репозиторий.

Проверка production (команды выполнять в shell с правами root через `sudo -n`):

  ```bash
  cd /root/projects/vidno/vidno
  docker compose ps
  curl -i --resolve vidno.one:443:127.0.0.1 https://vidno.one/api/health
  curl -I --resolve vidno.one:80:127.0.0.1 http://vidno.one/
  ```

Ожидается `200` для HTTPS `/api/health` и `301` с HTTP на HTTPS.

### Общий порядок серверных работ

- До любых изменений сообщить пользователю известный статус и конкретный план.
- Сначала выполнить read-only проверку `docker compose ps` и `/api/health` на том сервере, который планируется менять.
- Не менять домашний сервер при деплое на Timeweb.
- Не запускать скрипт обновления, не коммитить и не пушить без отдельного разрешения пользователя.
- Перед обновлением Timeweb проверить рабочее дерево:

  ```bash
  cd /root/projects/vidno/vidno
  git status --short --branch
  git fetch origin main
  ```

- Если есть локальные изменения, не выполнять `git pull` вслепую. Сначала сохранить их в именованный stash, затем использовать только fast-forward:

  ```bash
  git stash push -m pre-ff-YYYY-MM-DD-vidno-production -- <изменённые-файлы>
  git merge --ff-only origin/main
  ```

- После обновления снова проверить `git status`, `docker compose ps`, HTTPS `/api/health` и HTTP-редирект.
- Резервный stash не удалять без отдельного разрешения пользователя.

### Обновление сертификата Timeweb

- Подключиться к Timeweb-серверу и выполнить `umask 077`.
- Обновить CRT в `/etc/vidno/tls/fullchain.pem`, а private key в `/etc/vidno/tls/privkey.pem`.
- Выполнить `chmod 600 /etc/vidno/tls/*.pem`.
- Проверить конфигурацию Nginx внутри frontend-контейнера:

  ```bash
  cd /root/projects/vidno/vidno
  docker compose exec frontend nginx -t
  docker compose restart frontend
  ```

- После этого проверить срок и домены сертификата, HTTPS снаружи и `/api/health`. Private key не выводить.

## Безопасность

- Никогда не читать, не показывать и не изменять файлы `.env`, включая `backend/.env`.
- Не читать и не выводить токены, пароли, содержимое SSH-ключей и другие секреты.
- Не запускать команды, печатающие переменные окружения или содержимое окружения процесса/контейнера.
- Не добавлять секреты в код, логи, ответы, коммиты или команды.
- Не коммитить и не пушить без прямого разрешения пользователя.
- Не удалять контейнеры, Docker volumes, базы данных, кэш или логи без отдельного явного разрешения пользователя.

## Дизайн

Единственный источник цветов — токены в `css/style.css`. Не вводить новые HEX. Использовать светлую палитру Vidno в контенте и `--night` только для разрешённых тёмных поверхностей, включая левую панель рабочего dashboard. При изменении цвета проверить и CSS, и захардкоженные данные Chart.js/градиенты в JavaScript.
